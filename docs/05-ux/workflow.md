# UX 관리 방식과 MVP 화면 목록

- 상태: 관리 방식 확정(D125), 화면 분할·배치·상세 조작은 초안
- 담당: AI 작성·갱신, 사용자 방향 결정·플레이 피드백
- 변경일: 2026-11-27
- 근거: [첫 MVP](../01-vision/scope.md#첫-mvp-범위--d117), [결정 기록](../decisions.md), [화면 흐름](screen-flow.md)

## 기준과 연결

사용자 여정은 [user-flow.md](user-flow.md), 화면 전환과 처리 상태는 [screen-flow.md](screen-flow.md), 게임 규칙은 시스템 문서가 기준이다. 화면별 명세는 `screens/`, 공통 시각 규칙은 [디자인 시스템](../../design/mvp/design-system.md), 실행되는 UI 원본은 Godot Theme·공통 UI 씬에 둔다. Figma는 선택 도구다.

기존 `SC-` 화면 ID와 `ST-` 처리 상태를 유지한다. 별도 UX 번호를 중복 발급하지 않는다. 하나의 SC가 별도 씬·페이지를 강제하지 않으며 캠핑장 안 모드·패널도 같은 방식으로 식별한다. 이슈 제목·구현 참조·검증 기록에 해당 ID를 적는다. 화면 폐기·통합 시 기존 ID와 대체 관계를 남긴다.

## MVP 작업 목록

아래는 첫 MVP를 위한 작업 분해 초안이다. 기존 프로토타입과 일부 기능이 겹쳐도 새 UX 기준으로 검증되기 전에는 완료로 집계하지 않는다. 기존 ID는 그대로 사용하고 새 ID는 이 문서의 제안이다.

| ID | 사용자 목적 | 범위·상태 |
|---|---|---|
| SC-INTRO | 캠핑 분위기를 경험하고 바로 시작 | 기존 ID·명세 보완 예정 |
| SC-AUTH / SC-PLAY-RESUME | 인증하고 저장 진행으로 복귀 | 기존 ID·기존 구현 재사용 검토 |
| SC-CHARACTER-SELECT | 첫 시작 캐릭터 선택 | 기존 ID·[로컬 구현/검증](screens/character-select.md), 실기기 대기 |
| SC-FIRST-WEEK | 첫 업무로 수입 획득 | 기존 ID·[단순 수입 UI 로컬 구현/검증](screens/first-week.md), 실기기 대기 |
| SC-MVP-PLACE | 풍경·자리 크기·비용을 비교해 선택 | 로컬 구현·상세 달력 예약 제외 |
| SC-ITEM-SHOP / SC-SHOP-MENU / SC-SHOP-REVIEW | 장비·음식 구매 | 로컬 구현·MVP 소수 품목 |
| SC-FORECAST / SC-CLOTHING | 날짜별 예보 확인·옷 선택 | 로컬 구현·준비 화면/상시 예보 |
| SC-PACK | 제한 시간 내 출발 짐 적재 | 로컬 구현·시간 종료 후 자동 출발 |
| SC-CAMPSITE | 원하는 물건 배치·휴식·철거 | 로컬 구현·2D 에셋/투명 3D 격자 편집 |
| SC-COOKING | 음식 하나 조리·직접 먹기 | 로컬 구현·음식 하나, 다양한 레시피 후속 |
| SC-RETURN-PACK | 제한 시간 내 귀가 짐 적재 | 로컬 구현·미적재 손실·재도전 없음 |
| SC-WEEK-RESULT | 결과 확인·저장·다음 캠핑 연결 | 로컬 구현·정산과 다음 주 |

전체 한 주의 연결은 수입 → 장소/구매·예보/의상 준비 → 출발 적재 → 설치·캠핑·조리/식사·휴식 → 철거·귀가 적재 → 정산·다음 주다. 예보·의상 진입 순서와 귀가 결과 이후 자동 전환 등 미정 사항은 구현 전에 해당 화면에서 정한다. 신규는 인증·복원 확인 뒤 캐릭터 선택을 거치고 기존 진행은 저장 단계로 복귀한다.

## 화면 하나를 작업하는 순서

1. 사용자 목적·진입·주요 행동·전환과 규칙 근거를 명세에 적는다. 확정/AI 제안/미정을 분리한다.
2. 배치 확인이 필요하면 간단한 와이어프레임을 만든다. 텍스트 배치안이나 로컬 이미지도 가능하다.
3. Godot에서 공통 UI를 재사용해 작은 플레이 단위를 구현한다. 실제 파일 경로·관련 이슈를 명세에 연결한다.
4. 로직 검사, 실행 화면, 웹 입력, Android 실기기 검증을 구분해 기록한다. PC·폰·폴드 크기와 터치·클릭·키보드·패드 요구를 확인한다.
5. 문제를 이슈로 연결하고 수정 후 같은 시나리오를 다시 확인한다. 미실행 항목은 남긴다.

작업 상태는 `명세 초안 → 구현 중 → 검증 대기 → 검증 완료`로 관리한다. 검증 완료는 명세의 완료 기준과 요구 환경을 확인한 상태이며 일부 환경만 확인했다면 범위를 명시한다. 문서 작성·이미지 생성만으로 구현/검증 완료로 표시하지 않는다.

## 화면 명세에 필요한 최소 항목

ID·목적 / 근거 / 진입·종료 / 표시 정보·주요 행동 / 처리·오류·빈 상태 / 기기별 배치·입력 / 미정 사항 / 구현·이슈 참조 / 확인 가능한 완료 기준·검증 결과. 모든 화면에 대규모 문서를 만들지 않고 다음 구현 대상부터 작성한다.

## 현재 상태

관리 구조와 첫 명세에 이어 [Godot Theme·공통 UI 7종](../../game/ui/README.md) 및 독립 전시 씬을 추가했다. [렌더링 검토](reviews/2026-11-27-design-system.md)를 기록했으며 첫 캐릭터 선택 화면 연결과 입력 이벤트/저장 검사를 추가했다. 물리 장치 입력·실기기 검증은 남아 있다. 기존 생성 이미지와 Figma 보드는 참고 자료로 보존한다.

첫 MVP 전체 연결은 [구현 기준](../07-technical/mvp-v1.md), 검증은 [완주 기록](reviews/2026-11-27-mvp.md)으로 연결한다. 각 장소·구매·준비·편집/조리 모드는 하나의 공통 화면 씬 안에서 관리한다.
